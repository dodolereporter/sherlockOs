# ADR 0021: Private shell protocol and its client filter

- Status: proposed
- Date: 2026-11-25
- Lot: D-18a

## Context

The bar and the dock show fake workspaces, a fake active application and no open windows: the
compositor publishes nothing. They need, from the compositor:

- the windows: a stable id, title, `app_id`, states (maximized, fullscreen, snapped, minimized,
  active), geometry and screen, with an event on every change;
- requests on a window: activate, minimize, close;
- for the dock, a way to give the rectangle of the icon of each window, which the compositor
  keeps for the minimize animation of lot D-19;
- for the bar, per screen, whether a maximized or fullscreen window is on it (lot D-18b), and
  the workspaces: their list, the active one, and a request to switch;
- the workspace of each window, and a request to move a window to another workspace.

The compositor has no workspaces yet. Lot D-18w, right after this one, brings a fixed number
of them (3 by default, a setting), each window on one workspace, a sliding switch, Super + 1
to 9 to switch and Super + Shift + 1 to 9 to send a window, a click in the bar, and later
three-finger gestures. The protocols must model all of it now.

No standard protocol carries all of it. `zwlr_foreign_toplevel_manager_v1`, which the dock
already speaks, has neither the geometry nor the snapped state nor anything per screen.
`ext-foreign-toplevel-list-v1` has neither states nor requests. `ext-workspace-v1` (staging,
in wayland-protocols 0.32) covers the workspaces.

Whatever carries this lists every window and closes any of them: an ordinary client must not
reach it. The security notes of lot D-12 already ask for the shell's protocols to be kept to
the programs the session starts, and the brief excludes Flatpak applications and XWayland by
name. Two ways were open: recognize the client by the binary it runs, or by a socket of its
own.

## Decision

- **Protocol.** A private protocol, `sherlock_shell_v1`, version 1, in
  `desktop/shell-protocol/protocol/sherlock-shell-v1.xml`. Bindings for both sides are
  generated by `wayland-scanner` (crate `shell-protocol`, features `client` and `server`).
  `sherlock_shell_manager_v1` announces each window as a `sherlock_shell_toplevel_v1`
  (`id`, `title`, `app_id`, `state`, `output`, `geometry`, `closed`; requests `activate`,
  `minimize`, `close`, `set_rectangle`), the state of each screen (`output`,
  `output_removed`), and ends each batch with `done`. A compatible change bumps the interface
  version; an incompatible one makes `sherlock_shell_v2`.
- **Workspaces.** Through the standard `ext-workspace-v1`, served by the compositor itself
  (smithay 0.7 has no implementation): the list (`id`, `name`, `coordinates`), the active
  one (`state`), and switching (`activate`, applied at `commit`). What `ext-workspace-v1`
  does not carry goes in `sherlock_shell_v1`, naming the workspace by its `ext-workspace-v1`
  id: the `workspace` event of each window and the `move_to_workspace` request.
- **Workspaces shared by every screen.** One group holds every screen, and one workspace is
  active on all of them at once, as GNOME does by default. Reasons: Super + 1 to 9 then name
  one workspace without depending on where the pointer or the keyboard is; a window dragged
  to another screen keeps its workspace; a fixed number of workspaces is the same list on
  every screen; the reference laptop has one screen most of the time. Per screen workspaces
  (macOS, niri) remain possible as a setting: `ext-workspace-v1` then gives one group per
  screen, which a bar that shows the group of its own screen already handles, and nothing
  in `sherlock_shell_v1` changes. Until D-18w, the model holds a single workspace, `1`,
  holding every window.
- **Screens by name.** Screens are named by their `wl_output` name, rectangles are relative
  to the screen. The shell programs talk to these protocols on a connection of their own,
  where the `wl_output` objects of their surfaces do not exist.
- **Filter: a dedicated socket.** Next to the session's Wayland socket, the compositor opens a
  second one, the same name followed by `-shell` (`$XDG_RUNTIME_DIR/wayland-1-shell`).
  A client accepted there is marked in its client data; the globals of `sherlock_shell_v1`
  and `ext-workspace-v1` are only visible to marked clients (`GlobalDispatch::can_view`), and
  binding them by name without the mark is refused by wayland-server with
  `wl_display.error` `invalid_object`. Everything else is the same on both sockets.

Why the socket rather than the binary's path (`SO_PEERCRED`, then `/proc/<pid>/exe`):

- The path is read after the connection, from a process id that may already be another
  process, or the same process after an `exec`.
- Inside a Flatpak sandbox, `/proc/<pid>/exe` reads as the path in the sandbox: a runtime of
  one's own can hold a `/usr/bin/bar`. Comparing the device and inode of the file closes that,
  at the cost of more code.
- The list of allowed paths must follow where the shell is installed, and the binaries of a
  development build sit in `target/`.
- Neither stops a native process of the user outside any sandbox: it can connect to the
  shell socket, as it could launch the real `bar` with `LD_PRELOAD` under a path filter. The
  user's own unsandboxed processes are outside what this filter can defend.

With the socket, the decision is taken once, when the connection is accepted. Flatpak
(`--socket=wayland`) only puts the session's socket file in the sandbox, not the directory:
checked on the reference laptop with Flatpak 1.16.6 and Zen (`app.zen_browser.zen`, whose
permissions include `filesystems=host`), against a compositor of this lot listening on
`wayland-2` and `wayland-2-shell`: inside the sandbox, `/run/user/1000` holds `wayland-2` and
no `wayland-2-shell`. Our Docker sandboxes are to receive that one file the same way.
XWayland's connection is a socket pair that smithay creates, with smithay's client data, never
ours. The shell programs find the
socket from `WAYLAND_DISPLAY` (`shell_protocol::socket_from_env`).

## Consequences

- Lot D-18w fills `shell::workspaces::Workspaces` and the workspace of each window
  (`State::set_workspace_count`, `State::activate_workspace`, `State::move_to_workspace`), and hides the windows of the
  other workspaces: the protocols follow without change. Only the windows of the active
  workspace count in the per screen state.
- The bar (D-18b) and the dock (D-18c) open one more connection, to the shell socket, for
  these protocols. The dock's `windows::Source` and `windows::Control` get an implementation
  over `sherlock_shell_v1`; activation needs no seat.
- What a shell program launches inherits `WAYLAND_DISPLAY`, the ordinary socket: an
  application started from the dock sees nothing of the shell.
- A sandbox that is given `$XDG_RUNTIME_DIR` as a whole (`--filesystem=xdg-run/…` naming the
  shell socket, or a bind of the directory) reaches the shell socket. The rule for our
  sandboxes (lot of the Docker sandboxes) is to give the session's socket file only.
- The compositor computes the state of the windows after each loop iteration, only while a
  shell client is bound, and sends each client what changed for it: no hook in the rest of
  the compositor, at the cost of a pass over the windows per iteration.
- Minimizing exists from this lot: the window leaves the space and comes back at its place
  when activated. Client requests to minimize (`xdg_toplevel.set_minimized`,
  `_NET_WM_STATE_HIDDEN`) are not honored yet: until the dock can bring a window back
  (D-18c), a minimize button would lose the window.
- `zwlr_layer_shell_v1` is behind the same filter since lot D-46 (see the amendment below).

## What would change our mind

- A need to protect the shell from the user's unsandboxed processes: the compositor would
  then start the shell programs itself and hand each one an already connected socket, with
  nothing to find in the file system.
- Sandboxes that give applications the whole `$XDG_RUNTIME_DIR`.
- `wp_security_context_v1` used by every sandbox we ship: the filter could rest on it.
- A standard protocol that carries the geometry, the snapped state and the per screen state:
  the private protocol would then step back for it.

## Amendment (lot D-46, 2026-11-27): layer-shell on the shell socket only

The decision above left `zwlr_layer_shell_v1` open to every client. The security audit of the
session (27/11) showed what that allows: any application on the session's socket, a Flatpak one
included, can put an `Overlay` surface over every screen with an `exclusive` keyboard, draw an
imitation of the lock screen or of the polkit dialog there, and receive the password typed into
it, or keep the keyboard for as long as it wants. `ext-session-lock` cannot be imitated, but
layer-shell went around it.

- **Decision.** `zwlr_layer_shell_v1` is only visible to the clients of the shell socket
  (`WlrLayerShellState::new_with_filter`), as `sherlock_shell_v1` and `ext-workspace-v1` are;
  binding it by name from the ordinary socket ends in `invalid_object`.
- **The shell programs.** The bar, the dock, the notifications, the launcher and the
  applications view open their surfaces on a connection to the shell socket
  (`shell_protocol::connect`, given to `iced_exwlshell` as `ExWlSettings::with_connection`),
  found from the `WAYLAND_DISPLAY` that the session gives them. That variable itself is not
  changed: what these programs launch inherits the ordinary socket, so an application started
  from the dock or the launcher sees none of the shell's globals. Setting `WAYLAND_DISPLAY` to
  the shell socket for them would have handed it to every application they start.
- **The lock screen** uses `ext-session-lock` on the connection the compositor hands it, and
  needs no layer-shell. The volume and brightness indicator is drawn by the compositor.
- **The login screen** (`--greeter`) opens no shell socket and has one client, the greeter:
  `State::share_layer_shell` shows layer-shell to every client there.
- **Third-party programs.** None needs layer-shell today. One that would (a panel, a dock, an
  on-screen keyboard) goes through an ADR of its own, which says how it is started on the shell
  socket or which narrower right it gets.
- **What this does not stop.** A native process of the user outside any sandbox can still
  connect to the shell socket (see "Why the socket" above): the filter keeps the sandboxed
  applications, and the ordinary ones that only know `WAYLAND_DISPLAY`, out.
